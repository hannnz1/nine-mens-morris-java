# 九子棋并发控制调整：设计理由与面试说明

修改日期：2026-09-16。

## 一分钟面试回答

> 最初我使用 JPA 的乐观锁防止棋局被并发覆盖，同时用客户端版本号拒绝旧棋盘上的操作。重新分析业务后，我发现同一局棋本来就要逐步执行操作，而且一次操作主要更新一条棋局记录，事务很短，也没有外部网络调用。因此，我把加入对局和落子这两个写入口改为先取得棋局行的悲观写锁，再校验和更新。
>
> 修改的主要目的是让并发流程更直接，而不是宣称性能更高。例如，两个人同时抢最后一个席位时，后一个取得锁后会读到“对局已满”；相同操作同时重试时，后一个请求在锁内查到已提交的幂等结果，直接返回，不需要因为第一次操作改变了版本和回合而报错。
>
> 我保留了版本号和幂等键，因为它们分别解决旧棋盘操作和重复请求问题。锁只覆盖一次服务端事务，并设置等待超时。最后用真实 PostgreSQL 验证了抢座、重复提交、冲突操作、回滚和超时恢复等场景。

## 为什么修改

这个选择来自当前代码和业务边界，而不是“悲观锁比乐观锁高级”。

| 项目特点 | 对选型的影响 |
| --- | --- |
| 同一棋局的状态变化需要逐步生效 | 每局使用一个明确的互斥点，容易推理 |
| 一次操作主要修改一条棋局记录，另写一条幂等记录 | 锁范围清晰，可统一先锁棋局再访问幂等记录 |
| 事务内是本地规则计算和数据库访问，没有远程 HTTP 调用 | 持锁时间相对容易控制；实际耗时仍需监控 |
| 人类玩家轮流操作，单局写频率低 | 锁等待成本通常有限，但本次没有进行吞吐量对比测试 |
| 不同棋局相互独立 | 对不同 gameId 的操作不因同一条棋局行锁而互斥 |

低冲突不意味着必须使用乐观锁：它既意味着乐观锁很少失败，也意味着悲观锁很少等待。在这里，采用悲观锁的主要收益是让业务检查和幂等处理建立在取得锁后的状态之上。

原有乐观锁能避免丢失更新，没有证据证明它“错误”或“必须被替换”。原实现也没有复杂的自动重试框架。因此，面试时宜说“根据业务边界简化并发处理”，而不是把原实现定性为严重过度设计。

## 修改前后的具体差异

### 两人同时加入

- 修改前：两个事务都可能读到黑方席位为空，业务判断均通过，随后一个在写入时遇到乐观锁冲突，收到通用的版本冲突。
- 修改后：两个请求先竞争同一条棋局行锁。先取得锁的请求占位并提交，另一个取得锁后读取新状态，直接返回 `409 GAME_ALREADY_FULL`。

### 同一个落子请求同时重试

- 修改前：两个请求都可能查不到幂等记录。第一个提交后，第二个可能遇到版本冲突或回合错误，而不是直接得到原成功结果。操作不会因此被安全地重复执行，但恢复流程需要额外考虑。
- 修改后：取得棋局锁后才查询幂等记录。第一个提交棋局和幂等结果，第二个在 Read Committed 下取得锁后查询，就能看到已提交的原结果。相同凭证和载荷返回原响应，不同载荷复用同一个键返回 `409 IDEMPOTENCY_KEY_REUSED`。

### 两个不同操作基于同一旧版本提交

只有第一个成功操作推进版本。另一个取得锁后仍要校验 `expectedVersion`，得到 `409 VERSION_CONFLICT`。悲观锁不会自动让旧浏览器看到的棋盘变成最新状态，也不会保证任何排队操作都能成功。

## 代码改动

| 位置 | 改动 |
| --- | --- |
| `GameSessionRepository` | 增加带 `PESSIMISTIC_WRITE` 的 `findByIdForUpdate()`；普通 `findById()` 不加写锁 |
| `GameSessionService.join()` | 在 Read Committed 事务中先锁棋局，再判断席位 |
| `GameSessionService.performAction()` | 先锁棋局、鉴权、查幂等，再检查等待状态、版本和回合，最后执行规则并保存 |
| `GameSessionEntity` | 保留 `@Version`，解释其版本维护和防御性用途 |
| `GlobalExceptionHandler` | 将悲观锁获取失败映射为 `503 GAME_BUSY`；保留版本冲突处理 |
| 数据源配置 | 每条 PostgreSQL 连接初始化 `lock_timeout`，默认 `2s`，通过 `DB_LOCK_TIMEOUT` 调整；H2 测试使用对应的 H2 配置 |
| 浏览器 | 将 `GAME_BUSY` 显示为中文提示，没有新增自动重试机制 |
| 测试与 CI | 新增七个真实 PostgreSQL 测试，GitHub Actions 配置 PostgreSQL 16 服务 |

当前写入流程：

```text
事务开始（READ_COMMITTED）
  → 校验请求参数
  → 加锁读取棋局
  → 验证玩家令牌
  → 查幂等记录：命中则比较指纹并返回原响应/拒绝键复用
  → 检查等待状态、expectedVersion、当前回合
  → 规则引擎执行操作
  → 保存棋局并取得递增版本
  → 保存幂等结果
事务提交，释放行锁
  → afterCommit 推送棋局
```

注意：幂等命中必须在版本和回合检查之前。成功操作会改变版本、甚至切换玩家，合法重试不应被这两个变化挡住。新建对局使用新 UUID，不存在需要预先锁住的旧棋局行。

## 面试追问与回答

### 为什么还保留 @Version？这不是仍然有乐观锁吗？

是的，保留了版本维护和防御性乐观校验，不能声称已经删除所有乐观锁机制。但现有写入口的主要并发协调方式已经改成悲观行锁，不依靠先并发计算、再用版本冲突淘汰请求。

`@Version` 还负责自动递增版本，供客户端状态校验和 WebSocket 消息排序使用。删除它就需要额外维护版本递增，反而增加改动。JPA 允许对带版本的实体使用悲观锁。

### 既然锁住了，为什么还需要 expectedVersion？

行锁保护的是服务端一次事务里的并发修改。`expectedVersion` 表达的是“这一步操作基于哪一版棋盘”。玩家可能使用旧标签页，或者刚从断网恢复。取得数据库锁不能证明玩家看到了最新状态，因此这两种检查解决不同的问题。

### 为什么还需要幂等键？

两个完全相同的请求即使顺序执行，也仍然是两个请求。数据库锁只能控制同时修改，不能判断它们是否代表同一个用户操作。幂等键、请求指纹和已保存响应共同提供重试语义。

API 调用方在网络结果不确定时，应复用相同键、凭证、载荷和 expectedVersion 重试，不能为同一次重试生成新键。当前浏览器最多自动尝试三次；结果仍不确定时保留原请求供用户手动重试，不能据此声称端到端恰好一次。

### 悲观锁会不会把整张表锁住，或者锁到玩家下一步？

这里按主键取得选中棋局行的写锁，锁持续到这次服务端事务提交或回滚，不覆盖玩家思考时间。PostgreSQL 也会取得相应表级意向性锁，但不会因此把所有棋局的普通读写都串行化；普通 MVCC 查询也不会被这条行锁阻塞。本项目测试验证了持有一局锁时，公共 GET 和另一局落子仍可完成。

### 悲观锁是否一定更快？乐观锁是不是完全不加数据库锁？

没有这样的保证，本次也没有性能对比数据。悲观锁增加等待，乐观锁可能增加冲突失败或重试，两者要结合事务长度、竞争程度和恢复成本比较。乐观锁中的数据库 UPDATE 同样会取得必要的数据库锁，“乐观”描述的是冲突检测策略，而不是整个数据库执行过程中没有锁。

### 超时、死锁、回滚怎么处理？

PostgreSQL `lock_timeout` 限制锁等待时间；被 Spring 翻译为悲观锁获取失败的异常返回 `503 GAME_BUSY`，由调用方决定何时重试同一请求。它不是整个接口的总耗时上限。

所有现有更新入口都先锁棋局，再访问幂等记录，以减少锁顺序不一致。悲观锁不保证完全没有死锁；未来跨多局更新时还需要固定加锁顺序。事务失败会回滚棋局和幂等记录并释放锁，成功提交后才推送。

### 能用于多实例吗？

只要实例共享同一个 PostgreSQL 主库，并遵守相同加锁约定，数据库锁就能跨实例协调这些写操作。但整个系统的多实例部署还需要处理当前内存 WebSocket 连接表的跨实例投递。提交后推送也不等于可靠事件投递，进程在提交后崩溃仍可能丢失通知。

### 简化了什么，代码会更少吗？

简化的是同一棋局内“读取—检查—修改”和幂等查询之间的并发交错，以及冲突后的业务解释。代码行数不一定减少，因为增加了加锁查询、超时处理和并发测试。换来的是更直接的执行约定，同时承担短暂阻塞的成本。

## 验证记录与可以陈述的边界

2026-09-16，本地使用 Maven 3.9.11、JDK 21（项目主体编译目标 Java 17）和 PostgreSQL 16.2，在独立临时数据库执行全量 `mvn verify`：

| 测试组 | 数量 | 结果 |
| --- | ---: | --- |
| 规则引擎 | 7 | 通过 |
| 桌面适配回归 | 5 | 通过 |
| H2 API 集成 | 9 | 通过 |
| WebSocket 鉴权 | 1 | 通过 |
| PostgreSQL 并发 | 7 | 通过 |
| 合计 | 29 | 零失败、零错误、零跳过 |

七个 PostgreSQL 场景：并发抢座、相同请求返回同一结果、同版本不同操作最多一个成功、同键不同载荷拒绝、单局锁不阻塞普通读取和其他棋局、回滚后重试正常、超时返回 GAME_BUSY 且释放锁后可成功重试。

并发测试使用独立线程、真实事务和 MockMvc 经过控制器到数据库，通过 `pg_blocking_pids` 观察实际锁竞争。超时测试配置为 5 秒，给并发同步留出时间；应用默认值仍为 2 秒。前端 JavaScript 语法和 Docker Compose 配置检查也已通过。

没有 PG_TEST_URL 时，七个 PostgreSQL 测试显式跳过。CI 已配置运行它们，但本次没有推送或观察远端 CI 结果。上述验证不等于 HTTP 网络端到端测试、双浏览器实时同步测试、生产压测或线上稳定性证明。
