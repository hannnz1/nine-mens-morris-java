# 恢复、权限与简化设计

项目定位为个人开发和面试演示，单体部署、稳定表结构。保留规则引擎、短事务、按棋局悲观行锁、`@Version`、`expectedVersion`、幂等唯一约束；数据库沿用一份初始化 SQL、显式初始化与 Hibernate validate。

## API 契约

- `POST /api/v1/games`：`{"whitePlayer":"Alice"}`，201 返回等待棋局和白方凭证。删除创建双方及返回双方凭证的分支；旧 JSON 的额外字段不会创建黑方。
- `POST /api/v1/games/{id}/join`：`blackPlayer` 加 `joinToken`。客户端请求前用密码学随机源生成 32 字节、编码为 43 字符 Base64URL（无填充），持久保存后发送。服务端只保存 SHA-256 哈希。相同证明重复加入返回已分配黑方席位及当前快照，不改名、不增加版本；不同证明返回 `GAME_ALREADY_FULL`。禁止使用白方凭证作为加入凭证。
- `GET /api/v1/games/{id}`：公开快照，不返回原始凭证或哈希。
- `GET /api/v1/games/{id}/session`：携带 `X-Player-Token`，验证身份后返回快照；不存在为 `GAME_NOT_FOUND`，无效证明为 `INVALID_PLAYER_TOKEN`。
- `POST /api/v1/games/{id}/actions`：保留令牌、幂等键、原始动作及 `expectedVersion`。同一游戏行锁内先鉴权、查历史幂等记录，再检查版本、回合和规则。状态和幂等记录同事务提交。
- 原生 WebSocket `/ws` 只用于订阅服务器状态；见下方协议。页面和 WebSocket 使用同源部署。

## 失败恢复

`afterCommit` 只在提交后推送，发送异常被记录并隔离。数据库成功不会因通知失败变成接口失败，也不会为了重发通知回滚已成功的操作。

浏览器使用原生 WebSocket。连接打开只代表传输建立；客户端发出 SUBSCRIBE，收到服务端在鉴权及连接登记后返回的 SUBSCRIBED，再读取 REST 快照。每次重连重复这一流程。登记之前的提交由快照覆盖，登记后的更新也可通过推送到达。早于确认的状态消息不应用，确认后读取的快照补齐该窗口。每次轮询结束约 2 秒后再次读快照，补偿后续推送失败或断网遗漏；版本较旧的快照不会覆盖新版。轮询在重连期间继续，后台标签页定时器可能节流，不承诺严格的 2 秒上限。

每个异步请求/回调捕获会话代次和棋局 ID，结果仅可更新相同当前会话；`applyGame` 还校验棋局 ID 和版本。切换界面使旧代次失效。HTTP 请求 8 秒超时，轮询不重叠。

玩家身份、待确认加入证明、待确认动作保存在当前标签页 `sessionStorage`。返回入口只改变界面；恢复按钮继续原身份或原加入请求。临时断网、超时、5xx 不删除凭证；404/明确无效显示不同原因，由用户选择是否明确清除。本标签页只保存一份身份，建立新局前必须明确处理已有身份，避免静默覆盖。

一次新动作只生成一个幂等键，发送前保存原始 payload 和 expectedVersion；自动最多尝试 3 次，间隔 0.5/1 秒，每次请求有 8 秒超时。网络/5xx/408/429 和已识别并发冲突继续原请求；次数耗尽保留未确认状态，阻止新操作并显示手动重试。`GAME_BUSY` 同样复用原请求。确定业务拒绝清除待确认动作；`VERSION_CONFLICT` 额外刷新，不自动把旧操作改造成基于新版本的新操作。刷新棋盘本身不能证明不确定请求是否成功，不能据此丢弃待确认记录。

完整性异常只对 Hibernate 明确给出的 `uk_idempotency_game_key` 且 SQLSTATE 23505 映射业务冲突；其他约束异常记录服务端日志，返回通用 `INTERNAL_ERROR`，不把 SQL 或数据库详情发送给客户端。

## 维护负担

使用浏览器原生 WebSocket 和 Spring TextWebSocketHandler，移除 STOMP 客户端资源及专属许可证文件、simple broker、SimpMessagingTemplate 和消息通道拦截器。保留 spring-boot-starter-websocket 依赖；其传递依赖中仍可能有 spring-messaging，这不表示应用继续使用 STOMP。没有新增前端框架、消息队列或通用协议框架。

桌面 CandidateMgr 仅保留每局候选展示集合，集合不可由调用者修改；候选和提示管理器由每个 Game 独立拥有。旧 gather 规则及仅为它们服务的 Game 辅助方法删除，真实规则唯一由 game-engine 负责。保留桌面模块和回归测试。

Java 构建目标、桌面、CI 和 Docker 运行时统一为 17，Maven 3.9+、PostgreSQL 16。JUnit 与 Hibernate 版本由 Spring Boot 3.4.13 BOM 管理，删除桌面 Java 15 和额外 JUnit 覆盖。页面优先提供规则、邀请、恢复入口。

## 已有库手动处理

确认当前查询只有棋局主键读取和 `(game_id, idempotency_key)` 查找；没有按状态/更新时间列表查询，也没有按创建时间清理记录任务。因此删除 `init.sql` 中 `idx_game_sessions_status_updated`、`idx_idempotency_records_created_at` 两个非约束索引。主键、外键、唯一约束全部保留，幂等联合唯一索引也覆盖 game_id 前缀。

新的 init.sql 只适用于新库。已有数据库可以保留这两个索引，不影响程序正确性。确认无项目外部查询依赖、连接到目标数据库后，可独立手动执行（不要放进应用启动逻辑；CONCURRENTLY 不能在事务块内）：

```sql
DROP INDEX CONCURRENTLY IF EXISTS public.idx_game_sessions_status_updated;
DROP INDEX CONCURRENTLY IF EXISTS public.idx_idempotency_records_created_at;
```

不重跑初始化脚本、不删表、不重建数据卷。本次修复不自动对任何已有业务库执行这些命令。

## 接受的限制与面试说明

无账号系统；凭证是 bearer secret，丢失或显式清除后不能只凭姓名恢复。关闭标签页可能丢失 sessionStorage。创建白方仍是一次签发：创建已经提交但响应丢失可能留下无人继续的等待局；本次安全重试重点覆盖加入和游戏操作，没有扩展通用创建幂等框架。幂等记录没有自动过期清理，适用于演示规模；手动删除历史记录会缩短重放保证。推送不持久化，不保证每条消息都送达，快照提供状态恢复。

> 我按单体棋局的实际需求做取舍：一次操作只修改一盘棋，因此在短事务内锁定棋局行，让同局写入顺序执行。悲观锁解决数据库并发写，expectedVersion 防止玩家基于旧棋盘操作，幂等记录解决响应丢失后重复提交，这三者解决的是不同问题。提交后推送只是通知，失败不能否定已经提交的数据，客户端用快照恢复。加入身份通过预先保存的随机凭证证明，不能靠姓名认领。数据库结构稳定，所以只保留显式初始化 SQL 和 Hibernate 基本校验，省去版本迁移管理。我接受轮询带来的读取和同步延迟，不引入消息队列、分布式事务或发件箱，也不声称端到端恰好一次。

## 原生 WebSocket 协议

端点：同源 /ws；HTTPS 页面自动使用 WSS。玩家凭证只在连接建立后的首条 JSON 消息中传递，不放入 URL、不写入业务日志。沿用原有 SHA-256 凭证校验，不增加账号或连接凭证表。

| 方向 | 消息 | 处理 |
| --- | --- | --- |
| 客户端 → 服务端 | `{"type":"SUBSCRIBE","gameId":"UUID","token":"玩家凭证"}` | 仅允许首条鉴权订阅；只绑定一盘棋 |
| 服务端 → 客户端 | `{"type":"SUBSCRIBED","gameId":"UUID"}` | 已校验身份并登记连接；客户端现在读取 REST 快照 |
| 服务端 → 客户端 | `{"type":"GAME_STATE","game":{...}}` | 当前 GameResponse，全量状态含 ID 和 version |
| 服务端 → 客户端 | `{"type":"ERROR","code":"..."}` | 错误后关闭连接；不返回凭证或内部异常细节 |

服务端在当前单体内维护连接 ID 到连接及棋局绑定的表，广播只选取绑定相同 gameId 的已鉴权连接。断开、传输异常和发送失败都清理连接。连接表只服务通知，数据库仍是状态来源；应用重启后客户端重新连接并读取快照。

入站文本上限 1 KiB，二进制消息、额外字段、非法 JSON、未知消息类型、客户端伪造 GAME_STATE/操作、已鉴权连接再次订阅都拒绝。无有效证明或不存在棋局统一返回 INVALID_PLAYER_TOKEN；无订阅证明的连接在 5 秒后关闭。正常的原生 WebSocket 控制帧由框架处理，不实现业务 ACK 或消息队列。

广播使用 ConcurrentWebSocketSessionDecorator 串行化同一底层连接的并发发送，配置 2 秒发送时间检查与 64 KiB 缓冲限制。它不是对任意底层 I/O 的严格硬超时保证。单连接异常独立处理，不阻止继续尝试其他连接；提交后回调仍隔离通知异常。慢连接可能增加请求返回延迟，本演示项目不增加异步投递队列。

前端连接/确认等待上限 8 秒，临时断线约 2.2 秒后重连；明确身份或协议拒绝停止自动重连，保留凭证与 REST 快照恢复。返回入口会清理连接和所有实时定时器。连接回调同时检查棋局 ID、会话代次、实时连接运行代次与 socket 实例，旧连接不能重连或更新新会话。不新增应用层心跳，半开连接不承诺立即检测，周期快照保证在 HTTP 可用时仍可恢复棋局。

此协议替换不修改任何表结构，不需要运行初始化或升级 SQL。旧 STOMP 客户端不再兼容，需要重新加载当前网页；不提供双协议兼容分支。
