# 原生 WebSocket 改造记录

日期：2026-09-17。

## 结果与范围

实时通道从 STOMP 改为原生 WebSocket。REST 继续负责创建、加入和游戏操作；WebSocket 只推送提交后的完整状态；REST 快照负责首次同步、重连恢复及漏推送补偿。

未修改数据库结构、悲观行锁、`@Version`、`expectedVersion`、幂等重试契约和共享规则引擎。保留已有未提交改动，不提交或推送 Git，不对已有业务数据库执行初始化或升级。

## 实现

- `WebSocketConfig` 使用 `@EnableWebSocket`，同源 `/ws` 注册 `GameWebSocketHandler`。
- 删除 STOMP 的 broker 配置、授权拦截器、`SimpMessagingTemplate` 使用、前端客户端资源和该组件专属许可证说明。保留 Spring WebSocket starter；传递依赖中的 spring-messaging 不代表应用继续启用 STOMP。
- 首条 `SUBSCRIBE` JSON 携带 gameId 和玩家凭证。5 秒内未提供合法订阅则关闭；未鉴权连接不会收到棋局状态。鉴权完成先登记连接，再返回 `SUBSCRIBED`。不存在棋局和无效身份统一返回 `INVALID_PLAYER_TOKEN`。
- 每连接绑定一盘棋。重复订阅、客户端操作/伪造棋局消息、未知类型、非法 JSON、额外字段和二进制消息被拒绝。入站文本上限 1 KiB。凭证不进入 URL 或业务消息日志。
- `GAME_STATE` 包装原 GameResponse。广播按 gameId 选择已鉴权连接，使用 Spring 并发发送装饰器保护同一底层连接，单连接异常独立清理；提交后的总通知异常继续隔离。
- 前端原生 `WebSocket` 在确认后读取 REST 快照；连接和确认等待上限 8 秒，临时断线约 2.2 秒后重连，身份/协议拒绝停止自动重连。保留每轮读取结束约 2 秒后的周期快照、会话代次、棋局 ID、版本和 socket 实例检查。
- 更新 README 和现行恢复设计；修正旧文档中“浏览器没有自动重试”的过期说明。2026-09-16 修复报告保留为明确标注的历史记录。

完整消息格式及关闭行为见 [当前恢复设计](recovery-design.zh-CN.md#原生-websocket-协议)。

## 接受的限制

- 浏览器端验收使用真实网络和实际前端代码，但 DOM 为测试适配器，不代表图形浏览器视觉验收；桌面 GUI 未人工操作。Docker 容器运行和远端 CI 未在本轮验证。
- 推送不持久化、没有业务 ACK 或消息重放；进程提交后崩溃仍可能漏推送，后续成功快照恢复状态，不承诺端到端恰好一次。
- 保留周期快照，没有新增应用心跳；半开连接不保证立即发现。后台标签页定时器可能节流。
- 并发发送装饰器配置 2 秒发送时间检查和 64 KiB 缓冲限制，不等于任意底层 I/O 严格 2 秒硬截止。慢连接仍可能增加提交后返回延迟；为保持单体演示简单，没有额外投递线程池或消息队列。
- 旧 STOMP 客户端不兼容，需要重新加载当前页面。无需数据库迁移；不重新运行已有库的 init.sql。

## 面试说明

> 项目只需要给一盘棋的两位玩家推送状态，所以我用原生 WebSocket 加少量 JSON 消息，去掉通用 STOMP 协议和 broker。游戏操作仍走 REST，在短事务中完成鉴权、版本与规则检查，以及状态和幂等记录的保存。WebSocket 在鉴权和连接登记后明确确认订阅，客户端再读取快照；漏推送和重连由快照恢复。这个选择减少协议依赖，但也意味着我需要明确处理连接生命周期、并发发送和权限边界，不会宣称只是替换 API 就自动更简单或更可靠。
